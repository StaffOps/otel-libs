# Library overview and parity

The four helpers (Go, Python, Node.js, .NET) configure OpenTelemetry for a
service with one call and the same contract: the same environment variables,
the same precedence, the same defaults. This page lists what they share, where
they differ, and the full list of known differences in emitted telemetry.

**Audience:** application engineers choosing or upgrading a helper, and
reviewers checking cross-language behavior. Per-language detail lives in each
language's Overview and HOW-TO (left navigation).

## What one call configures

| Area | Behavior in every language |
|------|----------------------------|
| Resource | `service.name`, `deployment.environment.name` (when resolved), a per-process `service.instance.id` when the environment gives none, `telemetry.sdk.*`. Everything else (`k8s.*`, `cloud.*`) is added by the Collector |
| Propagation | W3C TraceContext + Baggage (`OTEL_PROPAGATORS`) |
| Sampler | `parentbased_always_on`; tail sampling happens at the Collector gateway ([ADR-002](https://github.com/StaffOps/otel-libs/blob/main/specs/decisions/ADR-002-parentbased-sampler.md)) |
| Health checks | Server spans for `/health /healthz /ready /readyz /live /livez /ping /metrics` and the `grpc.health.v1.Health` service are dropped; the requests stay in the HTTP duration metrics |
| Traces | Batch span processor → OTLP |
| Metrics | OTLP every 30 s; without an OTLP endpoint, a Prometheus `/metrics` listener on port 9464 ([ADR-007](https://github.com/StaffOps/otel-libs/blob/main/specs/decisions/ADR-007-keep-prometheus-in-core.md)); exemplars with the `trace_based` filter (Node.js: none) |
| Logs | The language's logging API bridged to OTLP, with `trace_id` / `span_id`; without a logs exporter, one JSON object per line on stdout |
| Application span failures | Error on a failure (no description, `error.type`), Unset on success, never Ok; the message and stack go to one correlated ERROR log record ([ADR-016](https://github.com/StaffOps/otel-libs/blob/main/specs/decisions/ADR-016-application-span-failure-status.md), [ADR-014](https://github.com/StaffOps/otel-libs/blob/main/specs/decisions/ADR-014-exception-detail-in-correlated-logs.md)) |
| Diagnostics | Configuration warnings on standard error, never with header values, client-key paths or URL userinfo/query |

The full environment-variable table is in the [Overview](../index.md#environment-variables-03-contract).

## Where the languages differ

The configuration contract is shared; the upstream instrumentations are not.
The main differences, by signal (the full list is the table at the end of
this page):

| Signal | Go | Python | Node.js | .NET |
|--------|----|--------|---------|------|
| HTTP server/client spans | `NewHTTPHandler`, `NewHTTPTransport` (otelhttp) | FastAPI / ASGI, requests, httpx | `node:http`, express, `fetch` (undici) | ASP.NET Core, HttpClient |
| gRPC spans | stats handlers (otelgrpc), current RPC semconv | legacy `rpc.*` attributes | legacy `rpc.*` attributes | client spans; server spans RPC-shaped only with an experimental switch |
| RPC metrics | `rpc.server/client.call.duration` | none | none | none (gRPC counted as HTTP, status 200) |
| Runtime metrics | `go.*` | `system.*`, `process.*`, CPython GC | none | `dotnet.*`, plus Kestrel, routing, DNS, memory pool |
| Exemplars | yes | yes | none | yes |
| Failure helper | `WithSpan`, `RecordFailure` | `traced`, `record_failure` | `withSpan`, `recordFailure` | parked (contract task A45 .NET) |
| HTTP/gRPC exception detail in logs (A37) | span text removed; no server record | server records | server records | parked (tasks C20, C21) |
| DB exception detail in logs (A36) | yes | yes | yes | yes (task C14a), without `db.system.name` on the record |
| Profiles | none | none | none | Pyroscope push package ([profiles](../observe/signals/profiles.md)) |

## How parity is enforced

The shared fixture `parity/cases.json` is run by every language's test suite
(config resolution, wire-level export, sampling, propagation, health
exclusion, logging, `/metrics`). A language that lags marks a case
`xfail:<reason>`; cases are never deleted to make CI green
([ADR-008](https://github.com/StaffOps/otel-libs/blob/main/specs/decisions/ADR-008-shared-parity-fixture.md),
[fixture README](https://github.com/StaffOps/otel-libs/blob/main/parity/README.md)).

## Known emitted-telemetry gaps

The configuration contract is shared; what the instrumentations emit is not
always identical:

| Area | Gap |
|------|-----|
| Python and Node.js gRPC | Spans carry the legacy `rpc.system`, `rpc.service`, `rpc.method` and `rpc.grpc.status_code` attributes, and no RPC metrics are emitted (upstream `opentelemetry-instrumentation-grpc`; `@opentelemetry/instrumentation-grpc` 0.300 in the Node.js helper, release candidate `0.3.0-rc.1`). Go emits the current RPC semconv and `rpc.server.call.duration` / `rpc.client.call.duration`. Node.js error spans also carry the non-semconv `grpc.error_name` / `grpc.error_message` (their `error.type`: row "SQL and gRPC span `error.type`") |
| Node.js gRPC handler that throws synchronously | Its SERVER span is never ended or exported (upstream `@opentelemetry/instrumentation-grpc`); Go and Python record the call with status UNKNOWN. Return errors through the callback or a rejected promise |
| Node.js routers created before `setup()` | An express app or router built before `setup()` gets a truncated `http.route` (`GET /api`) or none; require routes modules after `setup()` (the helper warns when express or grpc-js was loaded first) |
| Node.js HTTP/2 | `node:http2` servers and clients (h2c included) are not instrumented: there is no official HTTP/2 instrumentation |
| HTTP opt-in metrics | By default the instrumentation the helper installs records, in every language, only `http.server.request.duration` and `http.client.request.duration` (A30). With `OTEL_HELPER_HTTP_OPT_IN_METRICS=true` Python adds `http.server.active_requests` and the server body sizes (no client body sizes), Go the body sizes only (otelhttp has no active-requests metric), Node.js nothing (instrumentation-http records only the durations), .NET (branch, task C11) `http.server.active_requests` and its client metrics `http.client.active_requests`, `http.client.open_connections`, `http.client.connection.duration`, `http.client.request.time_in_queue` (ASP.NET Core and `System.Net.Http` have no body-size instrument; parity `skip:no-upstream-dotnet-http-body-size`) ([design D1](https://github.com/StaffOps/otel-libs/blob/main/specs/config-contract-v0.3/design.md), "HTTP opt-in metrics") The drop applies to the contrib instrumentations' scopes only, so an application's own instrument of those names is kept (Python: the FastAPI, ASGI, requests and httpx scopes, a closed list; another contrib instrumentation the app adds keeps its series) |
| .NET framework metrics (branch, task C11) | Besides the two HTTP durations, the .NET helper exports the series of the framework meters its instrumentations subscribe: `kestrel.*` (`active_connections`, `connection.duration`, `queued_connections`, `queued_requests`), `aspnetcore.routing.match_attempts`, `dns.lookup.duration` and the runtime `process.runtime.dotnet.*` (measured 2026-11-10 after one HTTP request, one HttpClient call and one gRPC call; other meters of the ASP.NET Core instrumentation, such as `Microsoft.AspNetCore.Diagnostics`, may add series in other code paths — not measured); Go, Python and Node.js have no counterpart. Drop what you do not need with `OTEL_HELPER_DISABLED_METRICS` |
| .NET gRPC metrics | No RPC metric (`rpc.server.*`, `rpc.client.*`) exists in the .NET instrumentations: a gRPC server call is counted in `http.server.request.duration` with status 200 even when the RPC fails, and a gRPC client call in `http.client.request.duration` as `POST` with status 200 and `network.protocol.version=2`. Go records `rpc.server.call.duration` / `rpc.client.call.duration` and no HTTP metric for gRPC. Parity `skip:no-upstream-rpc-metrics` |
| .NET log scope attributes (branch, task C17) | The .NET helper exports `ILogger` scopes as log attributes (`IncludeScopes`, as 0.2.x). In an ASP.NET Core request that includes the hosting scope `ConnectionId`, `RequestId` and `RequestPath` — the raw request path (e.g. `/order/1`), which is high cardinality and can carry identifiers; Go, Python and Node.js emit none of them. The activity-tracking scope (`SpanId`, `TraceId`, `ParentId`) is not exported (design D-NET10 (g)). To drop the hosting scope at the Collector (`transform` processor, contrib 0.160.0; validated and run against `dotnet-api` 2026-11-12: the three attributes gone): processor `transform/aspnetcore-request-scope` with `log_statements: [delete_key(log.attributes, "ConnectionId"), delete_key(log.attributes, "RequestId"), delete_key(log.attributes, "RequestPath")]`, listed in `service.pipelines.logs.processors` of the pipeline that exports the .NET logs (full YAML: [`dotnet/HOW-TO.md`](../dotnet/HOW-TO.md) §4) |
| .NET HttpClient health calls | Not traced and sent without trace context (as Go), but still counted in `http.client.request.duration`: the `System.Net.Http` meter has no path attribute to filter on |
| Node.js `http.route` | Only with express; a plain `node:http` server has no route on its spans or its server metric |
| URL redaction | Userinfo: Node.js clients write it as `REDACTED:REDACTED` (`node:http`; `fetch` rejects URLs with credentials and undici drops userinfo from the origin), Go drops it. Query values of `sig`, `Signature`, `AWSAccessKeyId`, `X-Goog-Signature`, `X-Amz-Signature`, `X-Amz-Credential`, `X-Amz-Security-Token`, `access_token`, `X-Goog-Credential` and `GoogleAccessId` are written as `REDACTED` in client `url.full` and server `url.query` in Go, Python and Node.js (contract D1 "URL query redaction", A28, A30; Go records no server `url.query`); other values (`token`, `api_key`), lower-case names and names without a value are kept; Python also redacts the status description and exception events of a failed request, but not under a foreign global TracerProvider. Don't put secrets in query strings |
| AWS attribute values | Aligned since A30 on the semconv v1.43 values: `messaging.system` `aws.sns` / `aws_sqs`, DynamoDB `db.system.name=aws.dynamodb` (plus the legacy `db.system=dynamodb` unless `OTEL_SEMCONV_STABILITY_OPT_IN` holds `database` without `database/dup`), `server.address`/`server.port` = the request host and port (Go and Python; Node.js below), every AWS call span named `<Service>.<Operation>` (Bedrock GenAI spans keep their name), kind CLIENT except SQS/SNS send and publish (PRODUCER) and SQS receive (CONSUMER), `messaging.operation.name` = the AWS operation on SQS and SNS spans, and the legacy RPC keys `rpc.system`, `rpc.service`, `rpc.method=<Operation>` by default — `OTEL_SEMCONV_STABILITY_OPT_IN=http,rpc` gives `rpc.system.name` and `rpc.method=<Service>/<Operation>`, `http,rpc/dup` both with `rpc.method` holding `<Service>/<Operation>` (contract D1 "AWS service attribute values", "AWS RPC keys"). Still different: SNS `messaging.destination.name` (Go the short topic name, Python and Node.js the ARN; none on a Node.js `PublishBatch`), SQS `messaging.destination.name` (Node.js only), `messaging.operation.type` (Go on SNS, Node.js on SQS receive), SNS `error.type` (`InvalidParameter` in Go and Python, `InvalidParameterException` in Node.js) |
| Node.js with a foreign TracerProvider | When another SDK registered the global TracerProvider first, the instrumentations use it, so the helper's health-check drop and gRPC status rule do not apply to their spans |
| Go resource from `OTEL_RESOURCE_ATTRIBUTES` | The Go SDK providers parse the variable again under the helper's resource (`WithResource` merges `resource.Environment()`): a blank `deployment.environment.name=` comes back as `""` instead of being absent, and a key with surrounding Unicode whitespace (e.g. U+00A0) is emitted twice, verbatim and trimmed. Python and Node.js emit only the helper's parse. Workaround: don't set blank values; use ASCII keys ([design D1](https://github.com/StaffOps/otel-libs/blob/main/specs/config-contract-v0.3/design.md)) |
| Go OTLP/HTTP endpoint path escapes | The Go exporters send the decoded path: `/a%2Fb` reaches the Collector as `/a/b` (`WithEndpointURL` keeps `url.URL.Path`). The helper warns once per variable. Python and Node.js send the path as written ([design D1](https://github.com/StaffOps/otel-libs/blob/main/specs/config-contract-v0.3/design.md), "Go: path escapes decoded") |
| Python IDN hosts | Python validates IDN labels by IDNA 2008 (`idna` package), so it rejects some hosts Go and Node.js accept — emoji, `_` next to non-ASCII text, labels over 63 characters, hyphens in the third and fourth position — as `<unparseable URL>` (empty labels and hosts over 253 characters are invalid in every language) ([design D1](https://github.com/StaffOps/otel-libs/blob/main/specs/config-contract-v0.3/design.md), "IDN hosts: Python residual divergence") |
| .NET IDN hosts (branch, task C7a) | .NET converts IDN hosts with `IdnMapping`: without ICU (globalization-invariant mode) a non-ASCII host is invalid (warned "needs ICU", or start fails for a code value); with ICU it rejects labels over 63 characters and labels starting or ending with `-`, as Python does; it depends on the image's ICU (measured with ICU 72; Windows not measured). Hosts `System.Uri` refuses (`a!b`, `a..b`) are invalid too ([design D1](https://github.com/StaffOps/otel-libs/blob/main/specs/config-contract-v0.3/design.md), "IDN hosts: Python residual divergence") |
| Exemplar filter (`OTEL_METRICS_EXEMPLAR_FILTER`) | Go (parsed by the helper since task A48; before, its SDK read the variable) and the .NET helper (branch, task C9: parsed by the helper, which always sets the filter because the .NET SDK default is `AlwaysOff`) honor `always_on`, `always_off` and `trace_based`, default `trace_based`. Python honors them too since task A33 (2026-11-18: the helper parses the variable at every setup, also with metrics off — contract trim, ASCII case-insensitive — and always passes the filter; any other value warns once, naming the variable and the value cut to 64 characters, and uses `trace_based`, where the Python SDK 1.42–1.45 alone would raise `ValueError`). Go follows the Python rule since task A48 (2026-11-19: the helper parses the variable and always passes the filter, because the Go SDK alone keeps an unknown value as `trace_based` without a warning and trims Unicode whitespace such as NBSP; case `metrics.exemplar_filter_env_invalid_warns` passes in Go); Node.js records no exemplars (sdk-metrics has no exemplar filter) ([design D1](https://github.com/StaffOps/otel-libs/blob/main/specs/config-contract-v0.3/design.md), "Metrics exporters / interval / exemplars") |
| Python log value-length limit with SDK 1.42 | `OTEL_LOGRECORD_ATTRIBUTE_VALUE_LENGTH_LIMIT=0` (or the generic `0`) is invalid by contract (warned, no limit), but the SDK 1.42 `LoggerProvider` takes no limits, so log attribute values are still emptied there; SDKs whose `LoggerProvider` accepts `log_record_limits` (1.45) follow the contract ([design D1](https://github.com/StaffOps/otel-libs/blob/main/specs/config-contract-v0.3/design.md), "Value-length limits") |
| Python with `OTEL_PROPAGATORS=none` | Fixed on this branch (task A34, 2026-11-10); **affected release `0.3.0rc3`**: every FastAPI request answers 500 under `none`, with or without trace headers. On `0.3.0rc3` leave `OTEL_PROPAGATORS` unset or use `tracecontext` / `baggage` until the next Python release candidate |
| OTLP redirects: gRPC diagnostic | Every language refuses OTLP redirects (task A31 for Go, Python and Node.js, 2026-11-18; .NET task C8): a `3xx` on an `http/protobuf` export is a failed export (the processor gets a failure; Python's exporter also writes its own export error, on both SDK bounds), never followed, with one ERROR per signal and status code (`redirects are not followed … signal=<signal> status=<code>`), never the `Location` or the response body. On gRPC no language follows a redirect, but only .NET writes that line for an HTTP/2 `3xx`; Go, Python and Node.js report the SDK's own export error (task A51) ([design D1](https://github.com/StaffOps/otel-libs/blob/main/specs/config-contract-v0.3/design.md), "OTLP export redirects") |
| .NET value-length limit 0 (branch, task C8) | `OTEL_ATTRIBUTE_VALUE_LENGTH_LIMIT=0` (or the span or log record variant) is invalid by contract; the .NET helper warns, but the OTLP exporter reads the variable itself (no public override) and sends those values empty; parity `skip:no-upstream-dotnet-attribute-limit` ([design D1](https://github.com/StaffOps/otel-libs/blob/main/specs/config-contract-v0.3/design.md), "Value-length limits") |
| Python `/metrics` scope labels on the lower bound | With `opentelemetry-exporter-prometheus` 0.63b0 (sdk 1.42) series carry no `otel_scope_name` / `otel_scope_version` labels; from 0.64b0 (sdk 1.43) they are written as in Go and Node.js (case `metrics.scrape_target_info_and_scope_label`, `python@sdk>=1.43`) |
| Go Prometheus names with a unit word, `total` or `ratio` inside | Go's exporter (`otlptranslator`) removes those words wherever they appear in the name: `probe.bytes-sent` in `By` → `probe_bytes_sent_total`, `req.total.count` → `req_count_total`, a Gauge `ratio.load` in `1` → `load_ratio`. Python and Node.js add a suffix only when the name does not already end with it (`probe_bytes_sent_bytes_total`, `req_total_count_total`, `ratio_load_ratio`) ([design D1](https://github.com/StaffOps/otel-libs/blob/main/specs/config-contract-v0.3/design.md), "Suffix semantics") |
| Go scrape with an `otel.scope.*` data-point attribute | A data-point attribute named `otel.scope.name` (or `_version`, `_schema_url`) makes Go's `/metrics` fail (`duplicate label names`); Python and Node.js keep the data-point value. Don't use those attribute names |
| .NET `/metrics` unit-`1` Gauges (branch, task C12) | The .NET exporter (`OpenTelemetry.Exporter.Prometheus.HttpListener` 1.20.1-beta.1) adds no `_ratio` suffix to a Gauge in unit `1` (`parity_utilization`, `ratio_load`); Go, Python and Node.js write `parity_utilization_ratio`. Parity `skip:no-upstream-dotnet-prom-ratio` |
| .NET `/metrics` colliding label values (branch, task C12) | Colliding attribute names are merged into one label, but the .NET exporter joins the values in attribute order (`a_b="y;x"`, `target_info{x_y="2;1"}`); Go, Python and Node.js sort them (`a_b="x;y"`). Parity `skip:no-upstream-dotnet-prom-label-order` |
| .NET `/metrics` bind address (branch, task C12) | The .NET `HttpListener` cannot bind an IPv6 literal or a dual-stack socket: every interface (unset, `0.0.0.0`, `::`, `[::]`) is every IPv4 interface (`::` also warns); `OTEL_EXPORTER_PROMETHEUS_HOST=::1` binds `127.0.0.1` (one warning); any other IPv6 address gets no listener (one ERROR, never widened). Go, Python and Node.js bind the IPv6 address. A host-bound .NET listener routes by the `Host` header: `127.0.0.1` also answers `localhost` for Go and .NET clients (the `localhost` prefix binds the resolver's first loopback address, `::1` when there is one); curl and Node.js, resolving with `AI_ADDRCONFIG` on a host whose only IPv6 address is `::1`, get 404 there and must use `127.0.0.1`; any other address answers only requests naming it |
| .NET on Windows: the `/metrics` listener (branch, task C19; not measured on Windows) | The .NET listener is `HttpListener` on HTTP.sys, whose default prefix `http://+:<port>/metrics/` needs an administrator or a URL reservation: a non-administrator process with no OTLP endpoint fails to start, with one `otelhelper: ERROR the Prometheus listener cannot bind: access denied …` line. Workarounds: an OTLP endpoint, `OTEL_HELPER_METRICS_PORT=0`, `netsh http add urlacl url=http://+:9464/metrics/ user=<user>`, or an elevated process; `OTEL_EXPORTER_PROMETHEUS_HOST=localhost` also registers a `127.0.0.1` prefix, not measured. Go, Python and Node.js bind a socket directly and need no reservation |
| Python disabled-metric patterns and mixed-case names | The Python SDK lower-cases instrument names, so `OTEL_HELPER_DISABLED_METRICS=Orders.*` matches `Orders.Total` in Go and Node.js but nothing in Python (warned once, the pattern is not echoed), and a lower-case `orders.*` drops `Orders.Total` in Python while Go and Node.js keep it (patterns are case-sensitive). Use lower-case instrument names and patterns ([design D1](https://github.com/StaffOps/otel-libs/blob/main/specs/config-contract-v0.3/design.md), "Disabled-metric patterns") |
| Stdout log fallback `logger` field | Python and Node.js write the logger name as `logger` in every line of the stdout JSON fallback; Go's `NewLogger` / `NewSlogHandler` take no name, so a Go line has a `logger` field only when the record (or its `With` attributes) carries a top-level `logger` attribute — written once, the last one winning. Pass `"logger", "<name>"` with `With` to get it on every Go line. The .NET branch (task C13) writes the logger category; parity case `logging.stdout_logger_field` is `skip:no-logger-name` for Go. The other fields — `time` (UTC, `Z`), `level`, `msg`, `exception` — are present everywhere; `exception` holds each language's native text (Go `Error()`, Python traceback, Node.js stack) ([design D1](https://github.com/StaffOps/otel-libs/blob/main/specs/config-contract-v0.3/design.md), "Stdout fallback fields") |
| Database error text in `exception.message` | Failed DB spans keep status ERROR without a description in every language (A25; Python on both `instrument_sql()` and the default `SQL` path of `setup_telemetry()`, not when other code instrumented SQLAlchemy first, which is warned), and on SQL spans the `exception` event keeps only `exception.type` in every language on this branch (Go XSAM's event, Python's `connect` span, Node.js pg; Python statement spans and Node.js mysql2 record none): the error text and the stack go to one correlated ERROR log record (task A36, [ADR-014](https://github.com/StaffOps/otel-libs/blob/main/specs/decisions/ADR-014-exception-detail-in-correlated-logs.md); Node.js pg and the mysql2 streaming form have no stack, as upstream hands the span no error object; mysql2 stacks hold no application frame). Redis (A26): the status rule covers it in every language (a known reply code — `WRONGTYPE`, `ERR`, `NOAUTH`, ... from a fixed allowlist — becomes `db.response.status_code` and `error.type`, anything else `_OTHER`, so a Lua `error_reply`'s first word never reaches an attribute; Python on redis-py < 8 reads it as `ERR`), and the exception event carries the server text, which for an unknown command or a Lua `error_reply` can quote arguments (`ERR unknown command 'X', with args beginning with: '<arg>'`); a Python pipeline error's event keeps the command names only (`Command # 2 (LPUSH ? ?) of pipeline caused error: …`). **SQL fixed in every language ([ADR-014](https://github.com/StaffOps/otel-libs/blob/main/specs/decisions/ADR-014-exception-detail-in-correlated-logs.md); Go, Python, Node.js: task A36): the event keeps only `exception.type` and the detail is in a correlated log record; Redis still keeps the server text in Go, Python and Node.js (task A52, owner decision pending)** |
| SQL and gRPC span `error.type` (design D16, R12) | Go on this branch (A38, A40, A44, A46): failed SQL spans carry `db.response.status_code` = `error.type` = the PostgreSQL SQLSTATE or MySQL server error number, else `error.type=_OTHER`; SQL spans and metrics carry `db.namespace`; gRPC CLIENT spans carry the canonical code name for every non-OK status and SERVER spans for the six server codes; HTTP server spans and `http.server.request.duration` carry the status code on 5xx (and 600–999). Node.js on this branch (A44, A46): failed `-sql` spans carry the SQLSTATE (pg, from instrumentation-pg's sanitized exception message) or MySQL server error number (mysql2, through instrumentation-mysql2's private `_patchCallbackQuery`; without it `_OTHER` and one WARN line), else `_OTHER`; the mysql2 streaming form (`query(sql)` without a callback) always `_OTHER`; gRPC CLIENT spans carry the code name for every non-OK status (`_OTHER` for a streaming client error without a code or a code above 16), SERVER spans for the six server codes (`UNKNOWN` for a server-stream or bidi handler error without a code). In Python a gRPC handler that fails without a code (a raising handler) leaves the SERVER span Unset while the peer receives `UNKNOWN` (Go: ERROR + `UNKNOWN`). In Node.js, callback-form calls (unary and client-streaming) whose handler or client callback fails without a code leave that span Unset with no `error.type` (instrumentation-grpc 0.300 sets no status; the client still receives `UNKNOWN` from the server, and grpc-js client errors always carry a code, so only a local or interceptor error reaches the client gap); a server-stream or bidi handler error without a code gives SERVER ERROR + `UNKNOWN`, as Go. Python SQLite spans keep contrib's file path in `db.namespace` / `db.name` and the span name (a documented residual, task A44); Python writes no `db.namespace` of its own (contrib's value is kept). .NET keeps its own values (parked) |
| Go SQL duration metric `error.type` | `db.client.operation.duration` carries the SQLSTATE / MySQL number as `db.response.status_code`, but its `error.type` stays XSAM's Go type name (`*pgconn.PgError`), not the code as on the span: XSAM v0.44.0 appends its own `error.type` after the helper's attributes (`utils.go:72`). For metric error rates select failures with `error_type!=""`, then break down by `db_response_status_code`. Separate upstream item, not part of A43 |
